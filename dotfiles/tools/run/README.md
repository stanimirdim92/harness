# run — tools you use during ticket work

These help while you work on tickets. They are optional: the pipeline
(intake → `/spec` → `/plan` → `/build` → `/test` → `/review` → `/ship`) works without them.

| File | What it does | Run |
| --- | --- | --- |
| `batch-fix.py` | Overnight: for every ticket whose last review left BLOCKER or REQUIRED findings open, runs `/build <TICKET> review fixes` in the worktree at the reviewed commit, and stops. Skips at the round cap, when the candidate moved, or when the checkout is not one ticket's alone (ambiguous, shared, dirty, detached or on main). Locks each checkout for the whole job. A job counts as built only on a BUILD COMPLETE line and a new commit; it saves that message to `<TICKET>-BUILD-COMPLETE.md` for you to paste into `/test`, then `/review`. BUILD BLOCKED or a CLI error fails it and the exit is non-zero. Never reviews, pushes or ships. | `dotfiles/tools/run/batch-fix.py --dry-run` |
| `pipeline.py` | Runs `/build`, `/test` and `/review` for one ticket, each in a fresh `claude -p` session, and passes each stage the previous messages verbatim. Review findings start a fix round, up to three reviews. Moves on only on BUILD COMPLETE, VERIFY PASS and a review count line with its review file; anything else stops it. Saves every message under `<git-common-dir>/handoff/`. Stops before `/ship`; never pushes (ADR 0114). The project's settings must allow the test commands, because `-p` sessions cannot ask. A stage that fails for a passing reason (rate limit, dropped connection, crash, or no event for `HARNESS_STALL_MIN` minutes, default 60) is retried up to `HARNESS_RETRIES` times (default 5), 10 s · 2ⁿ apart up to 5 min, resuming the same session; an auth or budget error stops at once. While a stage runs, a line every `HARNESS_HEARTBEAT_S` seconds (default 60) shows its time, event count and the last tool it called. Each finished stage is noted in `<TICKET>-pipeline.json`; started again on the same HEAD it goes on from the next stage. | `dotfiles/tools/run/pipeline.py <TICKET> --dry-run` |
| `ticket.py` | One ticket end to end (ADR 0115): intake and `/spec <TICKET> unattended`, then the High-risk questions and the defaults it took go to Slack (or the terminal). Only your thread replies that start with `TICKET ANSWERS:` count, so you can talk with the PO in the same thread; `1A 2B` answers, and `ok`, `go`, `approved` or the ticket id approves. A `?` in that reply gets an answer from the spec in the thread. The message numbers the defaults it took (`D1`, `D2` …) and lists your own earlier decisions; `D1: what you want instead`, last in the reply, has `/spec` rewrite that DEC as yours. When it stops, the message carries the reason and the stage output. Each stage, including `/build`, `/test` and `/review` inside `pipeline.py`, reports its time, cost and first lines in one thread per ticket; questions, stops, Back to spec and the `/ship` result go in the same thread and @-mention you there, so a ticket is one top-level message. Slack calls use `HARNESS_SLACK_MODEL` (default `haiku`). In any of the ticket's threads (run, questions, Back to spec, Stopped), `TICKET STOP` stops before the next stage and `TICKET NOTE: …` goes to the next stage's prompt; every start reads what you wrote while it was stopped, marks each read reply with 👀, and goes on from the last finished stage; `pipeline.py` gets your word before its first stage and between stages. `--until plan` pauses after an approved plan. A clean plan goes on by itself; then `pipeline.py` and `/ship`. Started on the default branch of the main checkout, it moves into the ticket worktree `.claude/worktrees/<TICKET>` (branch `worktree-<TICKET>`), because `/build` refuses the default branch; a missing one is made by `claude --worktree <TICKET>` itself (one tiny turn on the small model), so it gets the gitignored files `.worktreeinclude` names (`.env`, `vendor`, `node_modules` …) the way Claude Code copies them. `--help` prints the whole guide. A plan older than the spec's last commit is planned again. A SPEC CONFLICT from `/plan` goes back to `/spec` (unattended): a fix decided by default keeps your approval and planning goes on; a High one comes to you and the spec returns to Draft. A SPEC CONFLICT that `/build` routes to `/spec` (build.md names the stage per blocker) takes the same path, and the run plans and builds again on the commits made so far; any other BUILD BLOCKED stops. After two conflicts it stops. Commits, never pushes. With Slack it stays running and checks for your answer every 90 s for up to 8 h (`--wait`, `--poll`; `--wait 0` exits at once); after Ctrl+C, run it again to go on. Slack needs `HARNESS_SLACK_CHANNEL` and `HARNESS_SLACK_OWNER` (your email), and `HARNESS_SLACK_MENTION` (your Slack user id) to be @-mentioned; without them, answer with `--reply`. One run per ticket: `<TICKET>-ticket.lock` names the process, a second start is refused while it lives (exit 5) and takes over when it is gone; a run goes on from where the last one stopped. Between stages it also reads the ticket's Jira status: Done, or a status named in `HARNESS_JIRA_STOP` (default Blocked, On Hold, Paused, Cancelled) stops before the next stage like `TICKET STOP`; `HARNESS_JIRA_STOP=0` turns it off. Jira mirrors the run (`HARNESS_JIRA_WRITE`, default on): the start moves the ticket to `HARNESS_JIRA_START` (In Progress), the questions and a stop go on it as comments, and the `/ship` result is a comment with branch, HEAD and spend; GO moves it to `HARNESS_JIRA_REVIEW` (Code Review, or In Review). Only status moves and comments, through `claude -p` on the small model. `ticket.py --watch`, from the main checkout on its default branch, polls Jira every `--poll` seconds for open issues with the label `--label` (default `harness-run`) and starts a run for each, `--jobs` (default 2) at once, most urgent first; each child gets its own worktree, its output shows in the watch terminal with the ticket in front and is kept in `<git-common-dir>/handoff/<TICKET>-ticket.out`; each poll prints one line. The label is the claim: put it on to start, take it off to stop the run before its next stage. A run that reached `/ship` is not started again; one that stopped starts again once the ticket changes in Jira after the stop (the label taken off and put back counts, so does any edit); one that waits for you goes on at the next poll. Ctrl+C ends the watch and leaves the children running (they write their own `.out` file in their own session); a new watch leaves them alone while their lock lives. Exit 3 means it waits for you; 4, paused by `--until`; 5, another run holds the ticket. | `dotfiles/tools/run/ticket.py LD-1` |
| `run-metrics.sh` | Reads a finished session's transcript and reports what it cost: tokens, how well tool calls were batched, large file reads, and signs of trouble. `--row` prints a line for the observation log. | `dotfiles/tools/run/run-metrics.sh --help` |
