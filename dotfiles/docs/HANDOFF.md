## 1. What `ticket.py` is

`dotfiles/tools/run/ticket.py <TICKET|Jira URL>` takes one Jira ticket
through the whole harness, unattended except where risk needs a person
(ADR 0115, `dotfiles/docs/adr/0115-ticket-runner-end-to-end.md`).

```
intake (/jira-ticket) → /spec T unattended → ask in Slack → owner answers + approves
  → /plan (auto-approved when clean) → pipeline.py (/build → /test → /review, ≤3 rounds) → /ship
```

The owner's decisions, in force:

- **Questions.** Low and Medium risk take the recommended option as a
  `DEC-### … Decided by: default (unattended, ADR 0115)`. Only High-risk
  questions wait for him.
- **Spec approval** is his. A clean plan (`check-plan.py` passes, no
  `## SPEC CONFLICT`, no `OPEN QUESTION`) approves itself.
- **Commits and pushes.** The runner commits with a `Refs: T` trailer and
  never pushes. He pushes.
- **Plan conflicts.** A `SPEC CONFLICT` goes back to `/spec T unattended`.
  Fixed by default (no OPEN QUESTION left): his approval stands, he gets a
  note, `/plan` runs again. High-risk or behavior-changing: the spec goes
  back to Draft and he answers again. After 2 conflicts the run stops.
- **No per-stage time limit** as such; a stall (no event for 60 min) is
  killed and retried. He chose 60 min over Symphony's 5: a long test run
  makes no events.

## 3. How it works

### Setup in `main()`

1. `ticket_key()` takes a key or a Jira URL. `--watch` needs no ticket.
2. Refuses `master` and a detached HEAD.
3. `ticket_checkout()`: on the main checkout's default branch it moves into
   `.claude/worktrees/<T>` on branch `worktree-<T>` (`/build` refuses the
   default branch). A missing worktree is made by `claude --worktree <T> -p`
   itself (`claude_worktree()`, one tiny turn on the small model), so Claude
   Code applies `worktree.baseRef` and copies the `.worktreeinclude` files;
   verified live on 2026-10-20 (`.env` and `vendor` arrived). The worktree
   is left `locked` in `git worktree list`; harmless.
4. **Lock.** `claim()` writes `<git-common-dir>/handoff/<T>-ticket.lock`
   (pid, host, cwd, started). A live holder on this host → exit 5 (`BUSY`).
   A dead one is taken over. Released in `finally`. The lock comes before
   the dirty-tree check, because a running `/build` leaves the tree dirty.
5. `drive()`: refuses a dirty tree, builds the `claude`, `pipeline` and
   `Jira` helpers, runs `Run.go()` in the wait loop.

### Each stage is `claude -p`

`pl.claude(binary, prompt, budget, mode, log, tools, model)` runs
`claude -p --verbose --output-format stream-json --max-budget-usd B
[--allowedTools …] [--model …] [--resume <id>]` through `attempt_once()`:

- It reads the event stream line by line (`selectors`, 1 s ticks). The
  `result` event (or a bare `{"result": …}` object, which the test stubs
  print) is the answer; `session_id` is kept.
- **Stall:** no line for `HARNESS_STALL_MIN` minutes (default 60; 0 never)
  → `proc.kill()`, treated as transient.
- **Retries:** `HARNESS_RETRIES` attempts (default 5), waits
  `min(10 s · 2^(n−1), 300 s)` (`BACKOFF`), `pl.sleep` is replaceable in
  tests. `is_transient()`: a stall, any non-zero exit, or `TRANSIENT`
  (rate limit, 429/5xx, ECONN*, timeouts, "fetch failed" …) — unless
  `FATAL` matches (not logged in, authentication, 401/403, credit balance,
  billing, `max_budget`, `max_turns`). A retry with a session sends a short
  "your previous turn was cut off; carry on" prompt with `--resume`; without
  one it resends the original prompt. Cost adds up across attempts.
- The log gets the result line, stderr and each retry note, not every event.
- Permission mode is empty by default (the user's settings.json applies).
  `READ_TOOLS`: read-only Atlassian and Figma tools under several server
  prefixes; `HARNESS_ALLOWED_TOOLS` replaces the list. `JIRA_WRITE_TOOLS`:
  transitions and comments only. Slack and Jira calls run on
  `HARNESS_SLACK_MODEL` (default `haiku`) with a $1 budget.

### State

- `<git-common-dir>/handoff/<T>-ticket.json`: `ask` (ts, spec digest,
  seen), `thread`, `log`, `cost` (sum over stages, incl. pipeline stages),
  `conflicts`, `inbox_seen`, `inbox_threads`, `pipeline_done`,
  `jira_started`, `ship`.
- `<T>-ticket-<n>.md` per stage answer; `<T>-ticket.log`; `<T>-ticket.out`
  for children of `--watch`; `watch.log` for the watcher's own calls.
- `pipeline.py`: `<T>-<n>-BUILD|VERIFY|REVIEW.md`, `<T>-pipeline-stop.json`
  (why, last stage file), and **`<T>-pipeline.json`** (head, done, step,
  total, kept texts). Started again on the same HEAD it goes on after the
  stage in `done`; another HEAD starts fresh; a clean run deletes it. Stage
  numbers continue past any saved file, so a failed stage's message is
  kept. Its stage line prints `· stage N`, which `ticket.py` reads so the
  inbox file matches after a resume.

### `Run.go()` order

1. **Jira start.** If `jira_started` is not set: move the ticket to
   `HARNESS_JIRA_START` (In Progress); set the flag on success.
2. **Intake** when there is no spec: `/jira-ticket T`; stop if
   `docs/specs/T-intake.md` is missing. Then `/spec T unattended`, commit.
3. **`settle_spec()`.** `ask()` posts `ask_text()` to Slack and the same
   text, markup stripped (`plain()`), as a Jira comment. Only the owner's
   thread replies starting with `TICKET ANSWERS:` count. `split_redo()`
   takes the `D<n>: …` parts off the end; `parse_reply()` reads the rest:
   `1B1`, `Q2=B` answer; `ok`/`go`/`approved`/the ticket id approve;
   `defaults` takes the recommended options; a `?` gets an answer from the
   spec in the thread. Answers and D changes go to `/spec T decisions: …`;
   a changed default is rewritten as the owner's DEC. Approval sets the
   `Status`, `Approved by` and `Approved at` headers (`set_header` inserts a
   missing line).
4. **Plan.** `plan_stale()` (spec commit not an ancestor of the plan's) →
   `/plan` again. `has_conflict()` counts only a heading or the Handoff
   line, never prose. Conflict → `back_to_spec()`. Clean → `check-plan.py`,
   then approved.
5. `--until plan` → `PAUSED` (4).
6. **Pipeline.** `pipeline.py T --yes`, output streamed; each stage line →
   `pipeline_step()` posts progress, runs `check_inbox()`, writes
   `<T>-inbox.json`; `pipeline.py` waits for it up to 300 s.
7. **Ship.** `/ship T` with the last REVIEW message. The result is posted
   to Slack and as a Jira comment (branch, HEAD, spend, "nothing is
   pushed"); GO moves the ticket to `HARNESS_JIRA_REVIEW` (Code Review, or
   In Review).

### Between stages: `check_inbox()`

- Slack (when configured): new owner replies in the run thread, the ask
  thread and the latest conflict thread. `TICKET STOP` → stop;
  `TICKET NOTE: …` → appended to the next prompt.
- Jira, always: `jira_stop()` reads status, category and labels. Stops on
  category Done, on a status in `HARNESS_JIRA_STOP` (Blocked, On Hold,
  Paused, Cancelled), or, when `HARNESS_LABEL` is set, when that label is
  gone. `HARNESS_JIRA_STOP=0` turns the status part off. A read failure is
  printed and ignored.
- A stop posts to the run thread, leaves a one-line Jira comment via
  `stop()`, and the stage returns `stopped by the owner (<reason>)`.

### Slack

Through `claude -p` and the owner's Slack connector; the runner keeps no
token. `HARNESS_SLACK_CHANNEL`, `HARNESS_SLACK_OWNER` (email) and
`HARNESS_SLACK_MENTION` (Slack user id: the `<@id>` mention, and his
identity when haiku gives no email) live in his `.bashrc`/`.profile`, never
in the repo. Top-level with @mention: questions, stops, "Back to spec", the
`/ship` result. One "▶️ T · Run" thread per ticket for stage progress
(✅/❌, time, cost, first 6 lines; pipeline stages 🛠 🧪 🔍). Waiting: with
Slack the run polls every `--poll` 90 s for up to `--wait` 8 h; without
Slack, `--reply "1A ok"`. Exit codes: DONE 0, STOPPED 1, NOT_CHECKOUT 2,
WAITING 3, PAUSED 4, BUSY 5.

### Jira

- The owner's workflow (read live on 2026-10-20): Backlog → Selected for
  Development → In Progress → Code Review → QA → Ready for Release → Done
  (transition "Deployed"), plus Rejected. The defaults `JIRA_START` and
  `JIRA_REVIEW` match it. No labels were in use, so `harness-run` is free.
- Writes go through `Jira.change()` with `READ_TOOLS + JIRA_WRITE_TOOLS` on
  haiku; a failed write is printed and the run goes on (Jira mirrors the
  run, it does not gate it). `HARNESS_JIRA_WRITE=0` keeps Jira read-only.

### `--watch`

`ticket.py --watch [--label harness-run] [--jobs 2] [--poll 90]`, from the
main checkout on its default branch. Each poll: reap finished children,
`Jira.labelled()` runs `labels = "<label>" AND statusCategory != Done ORDER
BY priority ASC, created ASC`, then starts `ticket.py <KEY>` (with
`HARNESS_LABEL` in its env, stdout to `<KEY>-ticket.out`) for each key
until `--jobs` run. Each child's stdout is relayed to the watch terminal
with `KEY │` in front (`relay()`, a thread per child) and kept in
`<KEY>-ticket.out`; each poll prints one line. Rules: a key whose run reached `/ship` (state `ship`,
or exit 0) is never started again; exit 1 or 2 puts it in `held` until it
disappears from a poll (label taken off) and comes back; exit 3 or 4 goes
again at the next poll; a lock held by a run started by hand is respected.
Ctrl+C ends the watcher and leaves the children running. The owner chose
two at once and "label off = stop".

## 4. What the real run taught us (LD-503, `/var/www/html/leadbuster`)

LD-503 "Active Account Filter for Social Accounts", subtasks LD-504 (BE),
LD-505 (FE), LD-506 (QA); Laravel + React; remote named `leadbuster`;
default branch main. Bugs it exposed, all fixed and covered by tests: a URL
as the ticket argument; no output until the end; Slack and Jira MCP calls

line after the title; `1B1` answers); the dropped `Approved by:` line; a
stale approved plan reused after the spec changed; `/build` refusing main
(→ worktree + `.worktreeinclude`); a false SPEC CONFLICT from prose; a
rewritten spec bringing back a fixed scenario (`followers_min` without
`followers_max`; `AdvertiserBuilder.php:337` applies the range only when
both bounds are set — spec.md now says to keep earlier fixes and reuse the
owner's decisions); too much manual rerunning and scattered threads (→ the
wait loop, one thread per ticket, the conflict-approval rule). The second
session added the restarts at every passing failure, which is what §3's
retries, lock, resume and `--watch` answer.

The owner restarted LD-503 from scratch; its live state is on his machine.
The retry/`--resume` path and the Jira writes were tested against stubs,
not a real `claude -p`: **watch the first real run.** The log keeps the

## 5. Open items and ideas (not started)

- **A live session across a runner crash** is not restored (Symphony does
  not either); the retry covers API and network failures, the lock takeover
  the rest.
- **Jira comments as a channel.** The ask is mirrored to Jira but answers
  are read only from Slack (or `--reply`). Reading `TICKET ANSWERS:` from a
  Jira comment would let the PO's tool be the only tool.
- **Label removal is checked only between stages**, like everything else;
  a running `/build` finishes first.
- **Watcher as a service.** It is a foreground process (tmux). A systemd
  user unit with the `HARNESS_*` variables inline would survive a logout.
- **The `--watch` search and every status read cost one haiku call**
  (~$0.01, ~20 s). Fine at 90 s; revisit if polls get frequent.
- **App push notifications** are not implemented; the Slack @mention is the
  only notification.
